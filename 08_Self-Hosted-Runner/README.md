# GitHub Actions — Self-Hosted Runner

## 1. What is a Self-Hosted Runner?

A **self-hosted runner** is a server or machine that runs GitHub Actions workflows.

Instead of using GitHub's hosted runner, we can use our own machine such as:

* AWS EC2
* Linux Server
* Windows Server
* macOS machine

### Basic Flow

```text
Developer
    |
    | git push
    ↓
GitHub Repository
    |
    | GitHub Actions
    ↓
Self-Hosted Runner
    |
    | CI
    ├── Lint Frontend
    ├── Lint Backend
    ├── Build Frontend
    ├── Build Backend
    ├── Test
    |
    | CD
    ↓
Deployment
    |
    ↓
Application Server / Production
```

---

# 2. Why Use a Self-Hosted Runner?

A self-hosted runner is useful when:

* We want to run GitHub Actions on our own EC2 server.
* We need control over the runner environment.
* We need custom software/tools installed on the machine.
* We want to use an internal/private server.
* We want CI/CD jobs to execute directly on our infrastructure.

Example:

```text
GitHub
   ↓
GitHub Actions
   ↓
AWS EC2
   ↓
Docker / Kubernetes / Deployment
```

# 3. Create a Self-Hosted Runner

First, open the **GitHub repository**.

Go to:

```text
GitHub Repository
      ↓
Settings
      ↓
Actions
      ↓
Runners
      ↓
New self-hosted runner
```

Then GitHub provides runner configuration instructions.

---

# 4. Select Runner Operating System

GitHub asks us to select the operating system.

Available options can include:

```text
Linux
Windows
macOS
```

If our AWS EC2 instance is running Ubuntu/Linux:

```text
Operating System → Linux
```

For example:

```text
EC2
 |
 └── Ubuntu Linux
```

Therefore, select:

```text
Linux
```

---

# 5. Select Architecture

Next, select the architecture of the EC2 instance.

For a normal x86-64 EC2 instance:

```text
Architecture → x64
```

So our selection is:

```text
Operating System → Linux
Architecture      → x64
```

---

# 6. Create Runner Directory on EC2

Connect to the EC2 instance through SSH.

Example:

```bash
ssh -i my-key.pem ubuntu@<EC2-IP>
```

Create a directory for the GitHub Actions runner:

```bash
mkdir actions-runner
```

Move inside the directory:

```bash
cd actions-runner
```

Directory structure:

```text
/home/ubuntu/
        |
        └── actions-runner/
```

---

# 7. Download the GitHub Actions Runner

GitHub provides a `curl` command for downloading the runner.

The exact URL/version is provided by GitHub's **New self-hosted runner** page.

Example:

```bash
curl -o actions-runner.tar.gz -L <GITHUB-RUNNER-DOWNLOAD-URL>
```

Then extract the downloaded archive:

```bash
tar xzf actions-runner.tar.gz
```

After extraction:

```text
actions-runner/
├── actions-runner/
├── bin/
├── externals/
├── run.sh
└── config.sh
```

> **Note:** Use the exact download command generated by GitHub because the runner version and URL can change.

---

# 8. Configure the Runner

GitHub provides a configuration command similar to:

```bash
./config.sh --url https://github.com/<OWNER>/<REPOSITORY> --token <TOKEN>
```

Example:

```bash
./config.sh \
  --url https://github.com/anandkumarprajap/devboard \
  --token <RUNNER-TOKEN>
```

During configuration, GitHub may ask for:

```text
Enter the name of the runner:
```

Example:

```text
devboard-ec2-runner
```

It may also ask for labels.

Example:

```text
self-hosted
linux
x64
```

The runner is now connected to the repository.

---

# 9. Start the Runner

Run:

```bash
./run.sh
```

The EC2 terminal should show that the runner is listening for jobs.

Conceptually:

```text
EC2
 |
 └── GitHub Actions Runner
          |
          └── Listening for Jobs
```

Now GitHub can send workflow jobs to this EC2 machine.

# 11. Use Self-Hosted Runner in GitHub Actions

In the workflow YAML file, use:

```yaml
jobs:
  build:
    runs-on: self-hosted

    steps:
      - name: Checkout Code
        uses: actions/checkout@v4

      - name: Check Runner
        run: |
          uname -a
          docker --version
          git --version
```

The important part is:

```yaml
runs-on: self-hosted
```

This tells GitHub:

> Run this job on my self-hosted runner instead of a GitHub-hosted runner.

---

# 12. Self-Hosted Runner with Linux and x64 Labels

We can also specify labels:

```yaml
jobs:
  build:
    runs-on: [self-hosted, linux, x64]

    steps:
      - name: Checkout Code
        uses: actions/checkout@v4
```

The runner must have matching labels.

```text
runs-on:
[self-hosted, linux, x64]

        ↓

GitHub searches for a runner
with these labels

        ↓

EC2 Linux x64 Runner
```

# 13. Run Frontend and Backend CI

Our project can run frontend and backend CI jobs on the self-hosted EC2 runner.

Example:

```yaml
jobs:

  frontend:
    runs-on: self-hosted

    steps:
      - name: Checkout Code
        uses: actions/checkout@v4

      - name: Install Frontend Dependencies
        run: |
          cd frontend
          npm ci

      - name: Lint Frontend
        run: |
          cd frontend
          npm run lint

      - name: Build Frontend
        run: |
          cd frontend
          npm run build


  backend:
    runs-on: self-hosted

    steps:
      - name: Checkout Code
        uses: actions/checkout@v4

      - name: Backend Build
        run: |
          cd backend
          go build ./...
```

# 15. Deployment Using `./run.sh`

After CI is successful, the deployment stage can execute deployment commands on the EC2/self-hosted runner.

For example:

```bash
./run.sh
```

However, remember:

```text
./run.sh
```

normally means **start the GitHub Actions runner**.

It is different from an application deployment script.

For deployment, it is better to use a separate script such as:

```text
deploy.sh
```

Example:

```bash
./deploy.sh
```

A deployment script could contain:

```bash
#!/bin/bash

docker compose pull
docker compose up -d
docker compose ps
```

Then GitHub Actions can run:

```yaml
- name: Deploy Application
  run: |
    ./deploy.sh
```

---

# 16. Complete CI/CD Example

```yaml
name: CI-CD

on:
  push:
    branches:
      - main

jobs:

  # --------------------
  # Frontend CI
  # --------------------
  frontend:
    runs-on: self-hosted

    steps:
      - name: Checkout Code
        uses: actions/checkout@v4

      - name: Install Dependencies
        run: |
          cd frontend
          npm ci

      - name: Lint Frontend
        run: |
          cd frontend
          npm run lint

      - name: Build Frontend
        run: |
          cd frontend
          npm run build


  # --------------------
  # Backend CI
  # --------------------
  backend:
    runs-on: self-hosted

    steps:
      - name: Checkout Code
        uses: actions/checkout@v4

      - name: Build Backend
        run: |
          cd backend
          go build ./...


  # --------------------
  # Deployment
  # --------------------
  deploy:
    needs:
      - frontend
      - backend

    runs-on: self-hosted

    steps:
      - name: Checkout Code
        uses: actions/checkout@v4

      - name: Deploy Application
        run: |
          chmod +x deploy.sh
          ./deploy.sh
```

---

# 17. Important Difference: `run.sh` vs `deploy.sh`

This is important.

### `run.sh`

```bash
./run.sh
```

Purpose:

```text
Start GitHub Actions Runner
```

It keeps the runner connected and waiting for jobs.

```text
EC2
 ↓
./run.sh
 ↓
GitHub Actions Runner
 ↓
Waiting for jobs
```

### `deploy.sh`

```bash
./deploy.sh
```

Purpose:

```text
Deploy our application
```

For example:

```text
GitHub Actions
      ↓
Self-Hosted Runner
      ↓
./deploy.sh
      ↓
Docker Compose
      ↓
Application
```
